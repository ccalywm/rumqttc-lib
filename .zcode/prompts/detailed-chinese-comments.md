# 代码注释规范

你写的所有代码都必须附带**极其详细的中文注释**，目标是让初学者（甚至非程序员）也能看懂每一行代码的作用和原因。

---

## 核心原则：解释"为什么"，而不只是"是什么"

❌ 差的注释——翻译代码：
```
// 设置超时为30秒
setTimeout(30);
```

✅ 好的注释——解释原因：
```
// 设置超时为 30 秒：服务器处理批量导入平均需要 20 秒，
// 留 50% 余量防止网络抖动导致误判超时
setTimeout(30);
```

---

## 一、注释覆盖范围

| 代码元素 | 必须解释的内容 |
|---------|--------------|
| **文件/模块** | 这个文件在项目中的角色，和其他文件的关系 |
| **类/结构体** | 职责、生命周期、在系统中的位置 |
| **每个字段/属性** | 含义、类型选择原因、取值范围、默认值 |
| **每个公共方法** | 参数、返回值、错误处理、调用时机 |
| **关键代码行** | 这行在做什么，为什么这样做 |
| **复杂逻辑块** | 用流程图或步骤列表说明整体流程 |

---

## 二、六种注释技巧

### 技巧 1：术语即用即解释

遇到专业术语，用一句话就地解释，不要假设读者知道：

```
// JWT（JSON Web Token）是一种无状态的身份凭证，
// 服务端不需要存储 session，靠签名来验证 token 是否被篡改
```

### 技巧 2：类型选择要解释"为什么用它"

不能只说用了什么，必须说为什么选它：

```
// 用 ConcurrentHashMap 而不是 HashMap：
// 多个线程会同时读写缓存，HashMap 不是线程安全的，
// 并发读写会导致数据丢失甚至死循环
```

### 技巧 3：用"错误 vs 正确"对比展示易错点

```
// ❌ 错误：在主线程做网络请求，会卡住 UI
// let data = httpClient.get(url);
//
// ✅ 正确：用 async 在后台执行，不阻塞 UI
// let data = await httpClient.get(url);
```

### 技巧 4：用表格整理枚举/配置项

```
// | QoS | 名称 | 说明 | 适用场景 |
// |-----|------|------|---------|
// | 0 | AtMostOnce | 最多一次，可能丢 | 传感器数据 |
// | 1 | AtLeastOnce | 至少一次，可能重复 | 报警通知 |
// | 2 | ExactlyOnce | 恰好一次，最可靠 | 金融交易 |
```

### 技巧 5：用 ASCII 流程图展示复杂逻辑

```
// ```
// ┌───────────────────────────────────────┐
// │  外层循环（重连循环）                   │
// │  1. 检查是否被取消                      │
// │  2. 创建新的连接配置                    │
// │  3. 进入内层循环                        │
// │     ├─ 连接成功 → 订阅主题             │
// │     ├─ 收到消息 → 回调 onMsg()         │
// │     ├─ 出错 → 跳出内层循环             │
// │     └─ 取消信号 → 直接退出             │
// │  4. 等待 N 秒                          │
// │  5. 回到第 1 步                        │
// └───────────────────────────────────────┘
// ```
```

### 技巧 6：用时序图展示跨模块/跨语言交互

```
// ```
// 前端                        后端                     数据库
// ────                        ────                     ──────
// POST /login          →      验证密码           →     SELECT user
//                      ←      生成 token         ←     返回用户数据
// 保存 token 到本地
// ```
```

## 三、函数/方法注释模板

```
/// 中文概述（一句话）
///
/// 详细说明：在系统中的角色、被谁调用、何时调用。
///
/// 参数：
/// - `param1` — 含义（类型、约束、默认值）
/// - `param2` — 含义
///
/// 返回值：
/// - 成功时 — 返回什么
/// - 失败时 — 返回什么 / 抛出什么
///
/// 注意事项：
/// 调用者需要知道的约束或陷阱。
```

---

## 四、类/结构体注释模板

```
/// 中文名称和一句话概述
///
/// 详细说明：在系统中的角色和生命周期。
///
/// | 字段 | 类型 | 说明 |
/// |------|------|------|
/// | `field1` | `Type` | 用途 |
/// | `field2` | `Type` | 用途 |
```

每个字段额外补充：
- 为什么用这个类型（而不是别的）
- 初始值是什么、何时被修改
- 如果有多层包装（如 `Arc<Mutex<Option<T>>>`），解释每层的原因

---

## 五、禁止事项

1. **禁止**只写翻译代码的注释（`// 设置超时`），必须解释原因
2. **禁止** `// TODO` 或 `// FIXME` 不加解释
3. **禁止**省略"显而易见"的注释——对初学者来说没有什么是显而易见的
4. **禁止**注释和代码不一致——改了代码必须同步更新注释
5. **禁止**使用英文注释（行业通用术语除外：API、HTTP、JSON、JWT 等）

---

## 六、密度参考

- 每个**类/结构体**：≥ 10 行注释
- 每个**字段**：≥ 3 行注释
- 每个**公共方法**：≥ 8 行注释
- 每个**复杂逻辑块**（循环、分支、异步）：≥ 5 行注释
- 每个**关键操作行**（锁、指针、网络、异步等待）：1 行行内注释

**宁多勿少**：多余的注释可以删，缺失的注释让读者完全看不懂。
